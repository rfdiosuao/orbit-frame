## 调用时为什么用了 computer use

有两种不同目的：一是验证用户实际能否在页面上传、替换、连接和播放，必须经过可见交互；二是当时缺少足够方便的画布语义调用，团队需要在底层生成接口、素材路径和画布卡片之间手动衔接。

本轮 Chrome 原生文件选择器自动化异常，上传交互未完成。这只能说明这次 UI 验收中断，不能证明项目上传接口失效。已有二进制上传接口 `POST /v1/videos/frames`。最新源码又提供 `upload_frame`、`list_media`、`get_canvas`、`compose_video_scene`，以及 `generate_and_wait(canvas_id, card_id)`，已覆盖相当一部分此前的操作缺口。[MCP 定义](../scripts/orbit-frame-mcp.mjs)、[上传与路径转换](../scripts/frame-workflow.mjs)、[镜头语义操作](../src/canvas-scenes.js)

后续正常生产应通过这些工具完成素材导入、组装镜头和提交任务；computer use 用于最终画面检查与 UI 验收。

## 首尾帧与图生视频的验收边界

项目已有历史成功记录：仓库 [三入口压测报告](PRESSURE-TEST.md) 记录了 16:9 网页首尾帧、MCP 图生视频及云盘原片，并有对应本地证据文件。这份既有报告应保留；本次没有重新播放和核验全部历史文件，不能用它证明本轮指定模型与竖屏组合通过。

尤其要区别“上传和传参成功”“生成出 MP4”“视频实际采用原图”。此前 [画布审查](CANVAS-REVIEW.md) 已记录一条任务在附件访问失败后重绘素材：该视频虽可播放，却不能证明严格采用上传图。后续必须核对角色、hash、附件可读性，并观察成片首尾画面。

用户修复后，建议验收以下有限样本，而不是立即大量提交：

1. **导入与替换。** 三张可辨认图片，测试 A/B→C/A→B/C→A/C、交换、撤销重做、刷新；每个角色只有一个输入，共享图片不被替换连带改写。卡内替换不无故增加卡片。
2. **单图与双图。** 单图明确推导 image_to_video；双图明确推导 first_last_frame；只有尾帧、缺图片、显式文生模式却附图片时在生成前拒绝。
3. **参考图真实性。** 请求中的素材 hash 对应原文件；附件读取失败时明确失败，不能让上游重绘后仍报图生成功。播放观察角色、服装和首尾画面的实际对应。
4. **目标组合。** 用一个 5 秒、9:16、请求 Seedance 2.5 的图生视频作为首个探针；通过后再继续其他镜头。本次短剧还未验证这个组合。
5. **恢复与暂停。** 提交后丢响应、刷新、重启、同一节点重复调用都复用原编号；修改原图或文字不改变已提交的快照。暂停报告本地等待与上游任务两种状态。
6. **原片交付。** 视频必须 cloud_only 且 source_verification 为 matched_upload_path_and_size，随后验证实际文件解码、尺寸、时长、hash 与播放。不得只凭 MP4 魔数或普通视频卡文件判定交付。
7. **多人和规模。** 先两个调用者操作不同镜头，再测同镜头并发提交和旧版本冲突；逐步增加卡片，观察交互和媒体加载。当前存储上限为 500 卡、1000 连线，“无限”指空间，不代表无限容量或已测性能。

## 后续 Skill 的调用契约

优先复用已经存在的工具。Skill 应说明真实工具名、参数、输出与失败分支，避免让团队猜路径或拖拽坐标。

| 阶段 | 当前可复用入口 | Skill 必须说明 |
| --- | --- | --- |
| 连接与能力 | check_video_connection | ready 的范围、权限未探测、模型核验等级，不能以登录代替能力证明 |
| 素材导入 | upload_frame / list_media | 接受本地文件，返回规范 path、preview、尺寸和 hash；如何复用已导入素材 |
| 读画布与准备镜头 | get_canvas / compose_video_scene | canvas_id/card_id、提示词来源、首尾帧角色、默认模式与参数；准备步骤不生成视频 |
| 提交与恢复 | generate_and_wait / get_video_status | 原 task_id/request_key、超时与 unknown、输入冻结；不更换编号自动重发 |
| 原片交付 | download_video | 云盘原片验证、导出文件、hash、时长、比例及镜头对应关系 |
| 参考图生图 | 需要补齐统一 provider/edit 工具 | 上传原图、保存父子谱系、可查询任务；不能用 derived 连线代替真实参考图 |
| 取消与暂停 | 需要补齐统一入口 | 能否取消、取消回执、终态回读、哪些未知任务需要人工核查 |
| 剪辑交接 | 当前 edit-workflow.mjs | 每个镜头的原视频、task_id、hash、来源验证、字幕与音轨缺失；先 dry-run 再 render |

建议每个镜头保存 workflow_id、shot_id、canvas_id、card_id、task_id、请求编号，以及角色→资产→hash 的对应关系。图片和视频输出均保存 provider、requested_model、实际模型证据等级和来源；缺失字段明确留空。已有素材路径快照、幂等请求、SSE 状态和版本保护应继续使用。

最小恢复顺序：确认新工具在运行服务可用 → 验证两张现有图片的正规导入与画布显示 → 核查第三张原请求结果 → 验证真实图生图 → 单条目标视频探针 → 其余镜头 → 剪辑。第三张未知请求核查前不换编号重发。
